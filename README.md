# swift-phone-validator

Offline phone number validation for Swift — parse, normalise to E.164, and say
what KIND of number it is and where it was allocated. No network, no key, no
per-lookup cost.

The seventh library behind the `validate` CLI, beside
[swift-email-validator](https://github.com/arraypress/swift-email-validator),
`swift-iban-validator`, `swift-isbn-validator`, `swift-vin-validator`,
`swift-credit-card-validator` and `swift-uk-reg-validator`.

## What it can and cannot tell you

Read this before reaching for it, because "phone validation" is sold as one
thing and is actually three.

**What this does — offline, free, instant:**

- Parse a messy string into canonical E.164 — `07700 900123`, `+44 7700
  900123`, `(0770) 090-0123` all become `+447700900123`.
- Is it *possible* under that country's numbering plan? Not "does this number
  exist" — "could it exist".
- **Line type**: mobile, fixed line, VoIP, toll-free, premium rate, pager,
  shared cost, personal number, UAN, voicemail.
- **Which region** owns it, including telling apart the four territories that
  share +44 and the twenty-odd that share +1.
- Whether the region allows number portability — which is exactly why the
  carrier a number was *allocated* to is not necessarily who holds it now.

**What it cannot do, and no offline library can:**

- Say whether a number is **live, reachable or currently assigned**. That is an
  HLR lookup — a signalling query against the carrier's Home Location Register,
  sold per-query by telecom aggregators. It is not a phone call, the subscriber
  never knows, and it costs money.
- Name the number's **current** carrier after porting. Same reason.
- Prove anyone **owns** the number. That needs an SMS or a silent call, which
  is a verification product, not a validation one.

If a service claims to tell you a number is real, offline, for free, it is
telling you it is well-formed.

## Usage

```swift
import PhoneValidator

// International form needs no region.
let number = try "+44 7400 123456".phoneNumber()
number.e164              // "+447400123456"
number.region            // "GB"
number.type              // .mobile
number.isValid           // true
number.isMobilePortable  // true — so any carrier inferred from the prefix is
                         //        the ALLOCATED one, not necessarily current

// National form needs one. Every spelling below gives the same E.164.
try "07400123456".phoneNumber(in: "GB")
try "(07400) 123-456".phoneNumber(in: "GB")
try "0044 7400 123456".phoneNumber(in: "GB")

// Quick checks that never throw.
"07400 123456".isPhoneNumber(in: "GB")           // true
"07400 123456".e164(in: "GB")                    // "+447400123456"
["07400123456", "banana"].validPhoneNumberCount(in: "GB")  // 1

// Possible is a weaker, kinder claim than valid.
let fresh = try "+441111111111".phoneNumber()
fresh.isPossible   // true  — right length for GB
fresh.isValid      // false — not an allocated block
```

**Prefer `isPossible` when rejecting someone's input.** The metadata is
reissued fortnightly, so a genuinely new mobile block is possible before it is
valid, and turning a real customer away is worse than accepting a number that
later turns out to be dead.

Errors say what was wrong rather than returning a bare `nil`:

```swift
try "07400123456".phoneNumber()      // throws .regionRequired
try "banana".phoneNumber()           // throws .noDigits
try "07400123456".phoneNumber(in: "ZZ")  // throws .unknownRegion("ZZ")
```

## The metadata is the product

The numbering-plan data comes from Google's
[libphonenumber](https://github.com/google/libphonenumber), pinned to a
release and regenerated by a script in this repo:

```sh
./Scripts/generate-metadata.py            # the pinned release
./Scripts/generate-metadata.py v9.0.40    # bump
```

**Google reissues this metadata about every two weeks.** Stale metadata fails
in the worst possible direction: a newly-allocated mobile block reads as
INVALID rather than unknown, so the numbers that break are the newest ones, and
nothing announces it. Treat a metadata bump as a patch release. `MetadataStore
.sourceRelease` reports which release is baked in — print it in any `--version`
output, because it is the first thing to check when a real number is rejected.

The generated JSON is **committed**, so a bare clone builds with no network.

| | measured, v9.0.39 |
|---|---|
| source XML | 979,211 bytes |
| generated JSON | 224,557 bytes |
| regions / non-geographical codes | 245 / 9 |
| example numbers self-checked | 1,144 |

## Traps, all measured

**The XML pretty-prints its patterns.** A pattern reads
`[1-357-9]\d{9}| [18]\d{8}` — the space after the pipe is indentation, not
regex. Leave it in and every alternation branch after the first stops matching.
Measured against the metadata's own example numbers:

| | pass rate |
|---|---|
| whitespace stripped | **1144 / 1144 (100%)** |
| whitespace left in | 488 / 1144 (42.7%) |

It does not fail loudly. It just quietly rejects most of the world.

**`id="001"` is not a region.** It is libphonenumber's marker for the nine
non-geographical calling codes — +800 international freephone, +808 shared
cost, +870 and +881 satellite, +878/+882/+883 international networks, +888,
+979 premium rate. All nine carry the same id, so keying a dictionary on the
region id keeps ONE and silently drops EIGHT. They live in `nonGeographical`,
keyed by calling code.

**25 territories share +1, and the US will swallow all of them.** The US has no
`leadingDigits` and a `generalDesc` of `[2-9]\d{9}`, which matches every NANP
number including Dominica's. Resolving a shared calling code by "does the
general pattern match" sent the whole Caribbean to the US, where the
region-specific patterns then rejected it — **80 real example numbers reported
invalid**, measured. Regions carrying `leadingDigits` are chosen by a PREFIX
match on them; regions without are chosen only when the number resolves to an
actual line type there.

**A transform rule can ADD digits, so strip the trunk prefix once.** Barbados
parses with `([2-9]\d{6})$|1` and rewrites to `246$1`, expanding a local
seven-digit number into a full one. Applying that speculatively to each
candidate region let Barbados claim a Canadian 310-1234 service number and
return `+12463101234`. Strip once, using the main country's rules, before any
candidate is considered — which is what libphonenumber does.

**Ofcom's drama ranges are asymmetric, and it will cost you an afternoon.**
`07700 900xxx` is reserved for television, and libphonenumber EXCLUDES it from
the GB mobile pattern — so the number everyone reaches for when they want a
safe fake UK mobile reports invalid and the library looks broken. The landline
drama range `020 7946 0xxx` is NOT excluded. Both behaviours are asserted by
tests so nobody has to rediscover it.

All of these are asserted by tests, so a future metadata bump cannot
reintroduce them without the suite going red.

## Verification

The generator refuses to write a file whose patterns do not match their own
`exampleNumber` — free ground truth that ships inside the source data. The test
suite then runs the same 1,144 checks again **on the other side of the bundle
with ICU**, because `NSRegularExpression` and Python's `re` are different
engines and do not have to agree. They do, on all 1,144.

## Packaging — this library ships a resource

It is the only one behind `validate` that does, so it is the only one that can
be installed wrongly. Three scenarios, all measured on a release build:

| | result |
|---|---|
| binary + `.bundle` side by side | works |
| reached through a `bin/` **symlink** | **works** |
| binary installed **without** the `.bundle` | clean error, exit 5 |

That third row used to be a crash. SwiftPM's generated `Bundle.module`
accessor calls `fatalError` when the bundle is not found, which meant the tidy
error this library defines was unreachable and an installed-without-resources
binary died with `unable to find bundle named PhoneValidator_PhoneValidator`
and a stack trace. `MetadataStore` therefore locates the bundle itself and
never touches `Bundle.module`. Homebrew's `bin.install` takes the binary and
leaves the bundle behind, so this is the likeliest way to get it wrong.
